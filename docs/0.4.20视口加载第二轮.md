## 方案 1：完成结果重排与过期视频任务取消

原先排队任务会跟随视口更新，但已完成结果仍保留旧优先级，背压等待中的结果也不会再校验请求；视频封面/探测子进程离开视口后可能继续占用通道。

现在完成结果保留最初请求 key，在每次请求更新时按当前优先级重排，过滤 generation、源版本 key 或删除阻塞已失效的结果。清晰缓存可能以真实较大 key 交付，取消仍按原始预览请求 key 判断，避免把可用清晰结果错误丢弃。背压等待中请求失效只取消该结果，工作线程继续服务新视口；取消时清理对应的已交付标记，允许同一媒体以后重新入队。

自有 ffmpeg/ffprobe 子进程按当前请求检查取消，失效时只终止并等待本次创建的子进程句柄，不枚举或终止用户进程。可见尺寸任务不会因为自己的前台计数而被当作后台任务抢占；取消不触发重新探测回退，也不写成用户可见解码失败。没有增加并发，没有修改播放器 libmpv 参数。

新增测试覆盖：清晰 key 提升后仍按原请求保留/更新优先级、旧 generation/删除阻塞结果过滤、取消后重新入队、满队列过期等待者释放但工作线程不停止，以及真实自有 FFmpeg 进程取消。当前主程序 35 通过、2 忽略，日志 `artifacts/windows-app-tests-20261024T110432305.log`。内部 Release 构建和同路径性能复测正在进行，不能沿用基线的六组回归、安装/源码包和性能结果宣告本方案通过。

第三种初测照片整屏 6/10、半屏 8/10，较本轮原基线的 2/10 有覆盖改善，首张仍 10/10。但 32 秒工作集峰值 617.22MiB 超过 600MiB，不能宣布性能通过。

对视频原始加载记录复核发现：基线与第一种的 `video_first_ready_render_ms` 始终为空；第二、第三种分别有 460/462 条已渲染播放器记录，即混入了鼠标停留触发的悬停播放。第二、第三种约 52ms 的帧间隔和其他数值作为真实“加载＋悬停播放”混合负载保留，但不能与无播放的基线作纯加载因果比较。此前将此长帧直接归因于 33ms 快照的判断不充分，现更正。详细审计 `artifacts/viewport-hover-confound-audit.json`。
