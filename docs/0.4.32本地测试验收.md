# 0.4.32 异常小窗口修复与本地测试

2026-10-27。应用及安装器0.4.32，程序SHA256 `62d4ff86a179764b81fbd116540ed1cb741846c4963e8c3141a1dfaee7b92e0a`。只本地测试，具体源码、便携及实际安装校验以dist/0.4.32-local-test-20261027-window-recovery/delivery.json与verification/index.json为准；安装被用户主实例挡住时不宣称完整交付验证通过。

## 证据与边界

用户截图只有约一行品牌栏。只读Win32检查当前运行的0.4.29用户主实例PID492，主窗口最小化，DPI感知读取到正常恢复范围419×67物理像素，与截图吻合；没有移动、激活、恢复、关闭或读取该窗口的私人媒体。第一次未声明DPI上下文的虚拟化结果也保留，判断使用后续DPI感知记录。辅助事件/输入法窗口不当作主窗口。

锁定eframe构建未启用persistence，不能把问题描述为已证实的磁盘尺寸配置损坏。当前未设置最小窗口尺寸；旧实例IPC唤回仅取消最小化，无法修复损坏的正常恢复范围。因此反复点程序可继续转交同一旧实例，并不会重建正常尺寸。究竟哪个偶发系统事件最初把范围改小，尚未自然复现全部时序，不宣称根因链已完全闭合。

在独立的生成样本实例中，通过Win32设置可见窗口420×68、再最小化并注入同样小的恢复范围，然后由第二进程IPC唤回。旧0.4.31能稳定保留小尺寸，修复版同样流程三次恢复到之前正常大小；测试只控制新生成的自有PID，全部自动到时退出，没有关闭用户主实例。

初候选的三次小窗口恢复通过，但原生界面重排发现480×320下限及UI缩放时重发最小尺寸命令干扰正常窄窗。该失败、原截图和初候选精确源码保留；最终将原生下限收紧为320×180，UI缩放不重发原生最小尺寸，缩放切换后延一输入帧再判断。原820/1550pt重排门槛保持，新前缀重新运行，不能沿用初候选通过。

## 实际改动

普通窗口创建设置320×180原生逻辑点的下限。在App::logic检查异常小尺寸：有本进程最近一次正常尺寸时恢复它，否则使用原1100×760默认值，按当前显示器留边界限制；显示器过小时相应降低下限。正常半屏/用户缩放保持，异常请求250ms节流，状态大小固定且不写磁盘。

最小化、最大化、全屏时不发尺寸或最小尺寸命令，不把OS占位尺寸记作正常大小。锁定winit Windows的set_min_inner_size会重请求当前inner_size，所以这层隔离也覆盖最小尺寸更新。原生DPI与egui文字/UI缩放分开换算，缩放变动不应强行放大有效窗口。固定渲染面benchmark/seek诊断沿用原协议，本轮不作新性能通过结论。

新源window_recovery.rs负责有界恢复决策；main.rs设置初始下限，browser.rs负责调用，lib.rs导出模块；Cargo版本递增，依赖未变。保留第二排最左目录菜单、最右搜索/刷新/打开目录/设置四按钮组。媒体解码、缓存、generation/文件版本、视口优先、稳定几何、音画同步和媒体质量未改。这是功能稳定性修复，不追加第四种视频性能方案。
