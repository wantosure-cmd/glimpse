# 掠影 Glimpse 0.3.1：损坏索引恢复

日期：2026-10-21。应用 SHA256 `6f3e94a1cd45338b9d0592507268ab4eefaf3a1071531a214cb9073cdcde45e3`。本次应用与安装器版本增至 0.3.1，旧包保留。使用 Rust/egui/libmpv，保留已有功能、媒体原件和样式。

## 修复的实际问题

0.3.0 在专用数据目录放入损坏 `index.sqlite` 后，窗口能打开，但3秒原生观察中媒体数始终为0，目录中的合法PNG无法进入列表。原始损坏索引未改变；初次工具错误使用了 metrics 的 `samples` 键，随后只解析已有 `rows`，没有重跑或伪造退出码。基线证据保留。

0.3.1 为应用管理的派生索引增加恢复入口。在后台工作线程先验证文件头和SQLite quick_check，只有明确的 NOTADB/CORRUPT 才触发恢复：将原库及存在的WAL/SHM/journal移到同目录独立 `index-recovery-*` 备份，再创建新索引并重新扫描当前范围。状态栏显示恢复和备份位置，悬停可查看完整路径。媒体、配置、缩略图不被删除或改写。

高版本schema、数据库占用、权限/只读/IO错误不当作损坏处理，不自动重建。备份移动失败时尝试回滚，不能建立新库时报告错误及备份路径。目录/重解析文件不进入恢复。通用Repository与命令行 `--db` 保持严格行为；只有浏览器管理的索引显式启用，避免把用户指定的任意数据库当缓存替换。遇到占用应释放占用后重新启动，不承诺全部瞬时错误自动重试。

本功能是启动时管理索引重建，不是任意SQLite数据库修复，也不声称覆盖所有热日志/磁盘满/并发故障组合。损坏备份由用户保留，不自动清空历史备份。
