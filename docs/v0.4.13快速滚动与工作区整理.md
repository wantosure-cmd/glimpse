# 0.4.13 快速滚动与工作区整理

## 加载链路的变化

旧实现已经按视口生成解码请求，但解码完成后使用 FIFO 通道。快速滚动会让通道中剩下的旧视口结果继续占用交付名额，等待通道的工作线程也只检查退出，没有重新核对视口；UI 每帧两张的上传限制进一步放大这种排队。

本版将结果换为容量 8 的可裁剪队列：每帧刷新需求时丢弃过期结果，按最新视口优先级取结果，等待交付的工作线程再次检查 generation、当前需求和删除隔离状态。inflight 身份覆盖交付等待期，避免滚走再滚回来时重复启动相同任务。解码线程遇到同图正在解码时，先处理其他图片，让后续小图/清晰图复用已解码像素。

这相当于“先把眼前这屏画出来”，不是把 SSD 读满。文件读取、JPEG/HEIC 解码、缩放、磁盘缓存、GPU 上传是不同环节，磁盘 MB/s 不能单独代表加载性能。

保持原图比例、模糊预览后清晰图、图片方向和颜色转换；不降低缩略图清晰度、不扩大内存预算。结果最多 8 项、纹理预算 256MiB、解码像素复用预算仍为 128MiB，完整非 JPEG 解码线程仍为 2。JPEG 小预览复用缩放解码后的中间像素；更高清需求会升级缓存，不能把低分辨率结果当作原图。每帧最多处理 8 个结果，达到 3ms CPU 准备预算或 8MiB 像素预算后交给下一帧；这是 CPU 侧预算，并非硬性的 GPU 呈现时间保证。已经进入原生解码器的调用不会强杀，会自然释放；因此巨大 HEIC/PNG 的第一次解码仍可能慢。

## 验证

最终测试和 Release 原生回归结果、5000 项滚动对比及验收范围在本版 verification 中记录。滚动回调和就绪纹理指标不等于物理显示器呈现时间；不从某个队列指标直接推导所有图库都有相同比例提速。

## 工作区整理原则

整理前逻辑文件体积为 27.83GiB（不遍历 .git 和目录链接），其中 target/debug 为 7.91GiB，已作为可重建缓存清理。源码、assets、docs、tools、vendor、test-media 和当前交付包以哈希核对保持不变。

`tools/compact_workspace.py --current dist/0.4.13-local-test-20261023-scroll-priority` 只列计划；附加 `--execute` 才执行。需先完成编译/测试，工具不会终止运行中的程序。保留当前完整交付和 0.4.11 的 ZIP/安装器/源码作为回退；删除旧展开副本、过期二进制包和可重建编译缓存。

历史日志、截图、JSON、源代码副本以 SHA-256 去重写入 `artifacts/compact-时间/historical-evidence.zip`，校验归档后才移除原副本。可重建的编译/运行时二进制副本仅保留哈希，不重复归档；必要原生依赖在 vendor 和当前包中保留。历史证据原始路径移入归档，旧报告里的路径不代表仍有原位文件。

恢复某条历史证据到全新 target 目录：

```powershell
python -X utf8 tools/restore_compacted_evidence.py artifacts/compact-时间/historical-evidence.zip --prefix artifacts/原文件.json
```

恢复器核对内容哈希，拒绝覆盖已有目录，也不会把历史文件写回源码路径。

## 验收边界

本版不是完整首版已全部验收。Win11、干净断网 GPU、物理键鼠/系统 DPI/屏幕呈现和系统重启后的冷启动等缺口继续保留；旧版本证据不自动当作本版通过。第三方许可仍为本地测试交付，未替用户决定公开发行许可证。

## 未通过尝试

0.4.12 候选版在 5,000 项/120s 对比中，清晰就绪比例 94.5% 低于基线 96.2%，工作集峰值更高，未作为最终提速交付。另在 200% 应用缩放/小窗口下发现设置内容越界；本版约束设置内容与分类导航滚动范围，普通大窗口布局不变。原始日志和对比结果保留，不能覆盖失败记录。
