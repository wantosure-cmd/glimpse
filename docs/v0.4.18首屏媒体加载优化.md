# 0.4.18 首屏媒体加载优化

本轮关注启动或打开目录后，首张预览与首屏全部清晰预览出现的时间。窗口就绪、缓存文件生成、媒体实际绘制是不同指标，不能混用。

## 实现

1. 每次打开目录，后台索引在首份有效尺寸写入后立即发布一次快照，不再等待正常的 200ms 合并窗口。后续元数据仍按原有批量策略更新，保持索引、排序和布局的有界开销。缓存中已有的尺寸继续直接使用。
2. 至少 8 个逻辑处理器时，两个通用图片线程在没有图片排队时，可以协助生成当前可见区域的本地视频封面。最多两条协助线程；预取、尺寸探测和网络/虚拟路径不进入此分支。JPEG 专用线程不增加，全尺寸图片解码并行度不增加。
3. 保留可视区域优先、有界结果队列、每帧两张上传、256MiB 纹理预算、缓存格式和缩略图质量。保持目录折叠恢复位置以及现有播放和操作行为。

这项优化将原来闲置的线程用于首屏必要工作，并减少首次尺寸发布等待。它不依赖增加磁盘吞吐量，也不把提高任务管理器读盘数字当作优化目标。封面生成的主要代价还包括视频解码和进程启动。

## 测量方法与边界

`tools/compare_directory_firstscreen.py` 对明确指定的目录做只读测试，不写入任何媒体或标记文件。两个版本交替运行，各自使用隔离索引与缩略图缓存，再用相同缓存重开。记录原生绘制就绪信息和 100ms 采样的工作集，核对测试前后所有文件的大小与修改时间；并非全库内容哈希。

首次打开和缓存重开必须分别比较：重开时已有尺寸，首屏媒体数量可能不同，但同一阶段的两版需保持相同数量。保留所有失败与原始记录，不丢弃异常轮次。原生截图可能包含用户私人内容，只保留在本地诊断目录，不进入源码包或交付验证附件。

该结果是未清空操作系统文件缓存的本机应用绘制代理，采样间隔约 100ms，不是物理显示器呈现时间、系统冷启动、真实起播时间，也不能推导为所有磁盘或所有格式的固定提升。工作集树求和包含共享页重复计算，属于采样值。

## 证据位置

最终 release 与 0.4.17 在用户提供目录做 3 组交替对照，共 12 次运行；实际 84 个视频（57 MOV、27 MP4）。以下为中位数，样本量不足以宣称普适 P95：

| 阶段与指标 | 0.4.17 | 0.4.18 |
| --- | ---: | ---: |
| 首次打开：首张清晰封面 | 1.139s | 1.034s |
| 首次打开：首屏 16 张全部清晰 | 3.522s | 2.616s |
| 缓存重开：首张清晰封面 | 0.810s | 0.642s |
| 缓存重开：首屏 9 张全部清晰 | 0.810s | 0.756s |

首次首屏完整就绪时间缩短约 25.7%；首张缩短约 9.2%，提升较小，不应夸大。首次打开的“主程序与子进程工作集之和的采样峰值”中位数约 285.2 → 285.7MiB，最大观测值约 288.6 → 302.2MiB；这是有界并行的瞬时资源代价，并非所有媒体的固定内存上限。

12 次均正常退出且无缩略图失败；所有 84 个文件的大小/修改时间前后一致。当前构建 26 项主程序测试、86 项库测试通过，分别 2/1 项明确忽略。初次受限会话有 6 项系统权限相关库测试失败，已在普通桌面权限下补验通过，失败日志保留。原生目录、媒体导航、动效回归通过，21 个生成副本前后内容哈希一致，并已查看实际 FBO 截图。

没有在本轮重新验证全部格式矩阵、安装/卸载流程或独立解包源码再构建；交付包进行清单、源码字节与安装器载荷校验。环境缺少 rustfmt 组件，格式检查未执行成功，日志保留。试验阶段曾因测试工具把首次/重开的首屏数量混在一起断言而失败；工具改为按阶段比较，最终全组重测通过，旧记录未删除。

最终数据与功能回归摘要随本地测试包放在 `verification/`；原始私人目录诊断留在工作区 `artifacts/` 与 `target/directory-firstscreen-*`。此前试验数据与最终构建数据分别保留，不混算。

Windows 11 和物理输入/显示器验收仍未补齐，本轮不宣称完整产品验收通过。
