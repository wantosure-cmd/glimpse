# 掠影 Glimpse 0.4.4：回收失败诊断与当前构建验收

2026-10-22。本轮继续首版验收，保留 0.4.3 界面和全部业务行为。没有修改回收方式、解除安全检查，或用永久删除替代回收。

## 查明的问题

0.4.2 / 0.4.3 的扩展收藏清理脚本都报过“阶段 15 超时”。新增每秒阶段记录后，发现真实过程是：10 秒撤回期结束、媒体句柄释放、提交回收、Windows 返回失败，然后程序等待用户处理人工确认。脚本却先等待清理对象消失，尚未来得及读取回收失败，最终在 100 秒时才报超时。

现在先等待正在执行的批次结束，再检查失败和人工确认，最后才等待整个清理完成。受限会话复验在约 **16.3 秒**明确报告回收失败；完整清理专项仍为失败，没有把它改成“通过”。同时增加单独的负向安全检查：9 个生成文件前后哈希全部一致，空目录保留，人工确认仍待处理，没有执行永久删除。

诊断记录只在显式 `--features-smoke` 测试入口采集；正常浏览不记录这些逐秒状态。测试工具另外保存专用夹具的前后文件哈希，便于区分“有意回收”和“失败后原样保留”。

## 回收能力的对照验证

- 默认执行会话的进程令牌经实际查询为受限令牌；本地 D 盘的回收设置 `NukeOnDelete=0`，本轮没有修改注册表或 Windows 设置。
- 同一个 0.4.4 主程序，在经授权的普通桌面调用下，扩展收藏清理 **17 项全部通过**，含真实回收非收藏媒体、保留收藏/非媒体文件、移除空目录、撤回保护及关闭角落点击。
- 独立原生回收测试通过：专用生成副本经 Windows `IFileOperation` 进入系统回收站、执行原生恢复并核对内容；过期/占用文件保持原样，部分成功/失败统计正确。成功回收的回调标志为 642，包含回收位。库全套测试也覆盖嵌套非媒体目录回收与恢复。
- 对照支持“当前受限执行环境是此次失败的关键因素”的结论，不代表所有受限令牌、磁盘或系统都表现相同。Windows 未选择回收时仍然中止请求，只有用户单独确认后才允许进入既有永久删除路径。

API 语义依据微软的 [PreDeleteItem 回调说明](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperationprogresssink-predeleteitem) 与 [TRANSFER_SOURCE_FLAGS](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_transfer_source_flags)。保留回收位校验，不能为了让受限环境下的测试变绿而取消该校验。

## 未验证和限制

已重新初始化官方 computer-use 技能，使用隔离设置及生成/公共媒体启动普通桌面测试窗口。窗口可被发现，但 `get_window_state` 两次分别返回 `FrameArrived timed out` 和 `window capture timed out`；重新选择窗口后仍失败，按技能恢复规则停止输入，没有盲目发送鼠标/键盘操作。因此受控 egui 输入、GL 截图与 Windows 物理输入仍分开记录，不能把后者算通过。

Win11、物理输入/系统 DPI 切换、干净断网系统的完整 GPU 链路、真实 iPhone 10-bit / HDR、重启冷启动及物理 seek P95 等缺口保留。完整 Windows 首版仍未全验收，不能因为本轮 24 格式和回收测试通过就宣称目标完成。

只使用 `target/features-owned-*`、`target/test-fixtures/*` 等专用生成副本测试删除/恢复；未删除或旋转用户真实图库。应用许可证仍依用户选择暂未决定，本包仅供本地测试。
