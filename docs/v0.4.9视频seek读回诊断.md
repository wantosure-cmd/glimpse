# 0.4.9 视频 seek 读回诊断

2026-10-22，本地测试交付。应用SHA256：`05b62e11b46e42a1ee2a14b61311aaa896d7ae00f8188a86eabce7c0d21aa07b`。完整首版尚未全验收。

新增默认关闭的`--seek-benchmark <report.json>`，仅接受带`.seek-benchmark-owned`标记及20个参考目标的单视频生成夹具。普通启动不读取参考文件、不增加重绘或截图。原解码、播放、seek节流、样式及内存预算不改。

诊断将受控进度条按下/抬起事件送入真实egui控件，开始时间取raw-input hook注入按下事件时；由原有控件产生seek意图并经libmpv播放链路处理。在GPU截图回调中，要求目标附近进度（误差≤0.2秒）及画面中央标记颜色（每通道误差≤18）同时匹配，才记录完成时间。PNG编码在计时点之后；截图和读回本身开销包含在内。各样本持有独立完成槽，收集后不清空，防止迟到回调重复捕获或覆盖已记录图片。

夹具为自行生成的60秒1920×1080、30fps H.264运动测试画面，GOP60、20个非相邻目标，中央64×64颜色标记每3秒变化。明确声明颜色矩阵/范围，另用固定FFmpeg逐段解码核对实际标记像素。窗口截图中心对应实际视频区域，不以time-pos回调单独当作画面到达。20次全部完成才给P95，失败不丢弃，不用17次成功冒充完成。

三秒片段颜色不足以证明目标帧，因此进一步加入11位黑白逐帧编码（0–1799）。GPU截图必须读出帧号，换算帧时间与控件实际目标差≤2/30秒，同时进度与颜色条件满足才记录完成。夹具编码后用FFmpeg独立核对20个参考帧号；正式运行还要从保存的PNG中独立解码核对，不只相信应用报告。逐帧编码Debug20项通过，121.88ms仍仅为Debug探索值。

两次最初Debug试跑在17项后失败，均保留：无矩阵的纯色视频中，目标已到19.3秒，但GPU绿色通道171与预期192差21，严格拒绝匹配。补记录最后读回后确认该差异，未放宽阈值。随后明确声明矩阵，并改用运动画面及小标记；Debug20项通过，128.19ms仅为该次Debug就绪代理，不当作Release或验收结果。之后修复了收集完成槽后迟到回调可能重复保存的诊断生命周期问题，正式Release另行实跑，不混用先前构建哈希。

本工具测量“受控控件输入→目标位置及匹配GPU截图读回”，不是物理鼠标、显示器呈现、光子延迟或真实资源库的普适seek P95。即使数值低于500ms，也不能据此把规格中操作到真实新画面的性能验收标为通过。HEVC/4K、长GOP、网络盘及真实设备另报。
