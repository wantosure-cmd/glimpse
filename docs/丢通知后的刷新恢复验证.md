# 丢通知后的刷新恢复验证

日期：2026-10-19。当前分发程序仍为 `22349341e6ba7c7222040f74c8a3ab6b3085a037afa94cad0b1744750d4307dd`。本轮没有修改应用生产代码，只增加集成测试与验收记录。

## 场景与结果

新增 `tests/manual_refresh.rs`。使用真实 LibraryService、scanner 和持久 SQLite，而不是内存 mock：

1. 生成两份合法 PNG 原件，复制三张到专用相册目录，先完成扫描并写入已知尺寸元数据，然后关闭服务。
2. 在服务关闭、没有 WatchService 的阶段，同路径换成新尺寸 PNG、把一张专用副本移到扫描根外保留，再分别给当前子目录和兄弟目录新增副本。
3. 直接读取持久索引，确认它确实仍是旧的三项、已移走路径仍在、新增路径尚未入库；不以“理论上会丢通知”代替陈旧状态证据。
4. 重启服务并显式调用 `open_view`，这是 `Browser::refresh_in_place` 使用的服务边界。当前视图恢复为两项、祖先总数四项、两侧子目录各两项；移走记录清理，同路径替换文件保留 ID 并使旧元数据失效。
5. 在当前 generation 下提交旧指纹解码结果，用随后可见文件的有效元数据发布作为队列屏障，确认旧结果没有污染已替换文件；再提交真实新尺寸 24×18，确认成功写回且文件指纹一致。
6. 核对两个生成原件的哈希不变，移到根外的专用副本仍保留。此测试没有执行产品 Delete，也没有永久删除媒体。

运行：`cargo test --test manual_refresh --locked --offline -- --nocapture`。本轮新增一项集成测试通过；不声称本轮重新执行了此前全部 63 项测试。程序生产源文件及现有已交付 EXE 不变。

原始证据：`artifacts/manual-refresh-verification.json`、`manual-refresh-test.log`。初轮测试把 revision 误认为元数据写入计数，断言失败记录保留在 `manual-refresh-test-initial.log`；按需求以文件 fingerprint 和实际尺寸验证有效性，未修改产品代码来迎合测试。

## 范围边界

这是“服务关闭期间无法接收通知 + 持久索引 + 显式重扫 + 迟到元数据”的集成验证。没有制造真实 Windows 内核随机丢包，没有点击刷新按钮，不证明 UI 滚动锚点、选中状态、对话框或操作系统焦点的完整链路。因此 A17 继续为部分验证。

## 本轮 Windows UI 输入观察

专用空窗口首次捕获返回 `FrameArrived timed out: timed out waiting on channel`；重新选择窗口、激活并重试后返回 `window capture timed out: timed out waiting on channel`。遵循 computer-use 技能恢复规则，没有发送鼠标点击或键盘操作。记录见 `artifacts/os-ui-review-observation.json`，状态为 not_verified，不当成测试通过，也不把捕获工具错误当成软件功能缺陷。

仅本轮专用进程经路径、唯一数据目录和 PID 核对后停止，并确认已退出；没有关闭用户正常使用的其他应用。此前用户关于小键盘的人工反馈仍独立保留，不等于本轮目录选择或多选已经通过。
